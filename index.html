Getting Started

Introduction

Everything you need to install, launch, and start working in FidentraOS.

This manual explains how to install and get started with FidentraOS, based on the official setup package (FidentraOS-Setup, version 0.1.0, build 14).

This manual is being built up module by module from real screenshots. My Place (Dashboard), Asset, Log Book, Load Record, Job Request and Files are documented — the rest of the sidebar fills in as screenshots are supplied.
Getting Started

System Requirements

What the target machine needs before installing.

The setup package is a Windows installer (32-bit PE executable, built with Inno Setup 6). At minimum, the target machine should meet:

  • Operating system: Windows 10 or later (64-bit recommended)
  • Administrator rights, for installing the software and any required components
  • Sufficient free disk space (the installer package itself is approximately 19 MB; installed size may be larger)
  • An active internet connection, if FidentraOS communicates with a server or license service
Confirm exact minimum RAM, disk space, and supported OS versions against FidentraOS's official specification before distributing this manual.
Getting Started

Installing FidentraOS

FidentraOS uses a standard Windows installation wizard.

  1. Locate the downloaded file, FidentraOS-Setup-0.1.0(14).exe, and double-click it to launch the installer.
  2. If prompted by Windows User Account Control, select "Yes" to allow the installer to run.
  3. On the Welcome screen, review the introductory text and click "Next" to continue.
  4. Read the License Agreement. Select "I accept the agreement", then click "Next".
  5. Choose the destination folder where FidentraOS will be installed, or accept the default location, then click "Next".
  6. Choose the Start Menu folder for shortcuts, then click "Next".
  7. Select any additional tasks, such as creating a desktop icon, then click "Next".
  8. Review the installation summary and click "Install" to begin copying files.
  9. Wait for the progress bar to complete. This may take a few minutes depending on your system.
  10. On the final screen, click "Finish" to exit the installer. Leave "Launch FidentraOS" checked if you want to open the application immediately.
Exact wording of each screen may vary slightly depending on how the installer was configured. Confirm against the live installer and adjust step text if needed.

Asset — Groups & Asset Creation

Create the asset-group hierarchy, then create assets under the right group.

ModuleAsset
Main ScreenAsset Register
Primary PurposeCreate, organise, view and maintain fleet asset records.
Training OutcomeUser can create an asset group, create an asset, open Asset Details and understand each related tab.

Training Objective

  • Create the asset-group hierarchy using Tree View.
  • Create an asset and enter its identification, vehicle and business information.
  • Find the created asset in the Asset Register.
  • Open Asset Details and understand each tab.
  • Understand how related records from other modules appear against the asset.

Overall Asset Process Flow

  1. Create Asset Group — define the parent/child grouping.
  2. Create Asset — select group and enter asset details.
  3. Asset Register — verify the new asset in Tree View / list.
  4. Open Asset Details — select View to open the asset.
  5. Review Related Tabs — checklist, jobs, logbooks, requests, documents, readings and maintenance.

Step 1 — Create an Asset Group

Asset Groups organise assets into a logical hierarchy. The Asset Register uses Tree View to display these groups and their child groups, making it easier to classify and locate assets.

  1. Select Asset → Asset Register.
  2. In the Asset Groups panel, select Add Group.
  3. Enter the Group Name.
  4. Enter a short Description, if required.
  5. Select Create.
  6. The new group becomes available in the Asset Groups Tree View.

Step 2 — Create an Asset

After the required group is available, create the asset under the appropriate group. The New Asset form captures the asset's identity, registration, technical information, vehicle configuration and business information.

  1. Select Add Asset from the Asset Register.
  2. Select the Asset Group.
  3. Enter Asset Name and Asset No. as required.
  4. Enter registration/fleet information and vehicle identification details.
  5. Enter make, model, year and engine number where applicable.
  6. Enter VIN/Chassis Number, GCM, GVM, odometer and tare weight.
  7. Select Vehicle Type and then the relevant Axle Group.
  8. Set Status and complete description, department, customer and contractor where applicable.
  9. Select Create to save the asset.

Step 3 — Asset Register and Tree View

Once the asset is created, it is available in the Asset Register. The left side is the Asset Groups Tree View, while the right side contains the asset list. The user can expand groups to see child classifications and use search/filter controls to locate a specific asset.

Checklist — Asset Safety Checks

The Checklist tab shows the checklist assigned to the asset. In the supplied screen, both Pre-Start and Post-Trip checklists are displayed. Checklist templates are configured in Settings and the relevant checklist can then be associated with the asset.

  • Pre-Start — safety checks before operation, such as engine oil, coolant, tyres, brakes and lights/indicators.
  • Post-Trip — checks after operation, such as vehicle damage, fuel, tyres, warning lights and faults.

Job Order — Asset Work Orders

The Job Order tab provides the asset-level history of work orders. Status tabs allow the user to focus on specific stages. Job orders originate in the Job Order module and are linked to the relevant asset.

  • All — displays all linked job orders.
  • Assigned / In Progress — shows work at active stages when records exist.
  • Completed — shows completed job orders.
  • Cancelled — shows cancelled job orders.

Logbook History — Asset Log Books

The Logbook History tab shows log book records associated with the selected asset. Log books are created through the Log Book module; the asset's history provides a quick reference to submitted records.

  • Date/time identifies when the log book record was recorded.
  • Status such as Submitted indicates the current record state.

Job Request — Asset Requests

The Job Request tab shows requests associated with the asset. A request can be Open, Approved or Declined. Requests are created in the Job Request module and linked to the selected asset.

  • Use the status tabs to filter the request list.
  • Open requests require attention or further processing.
  • Approved requests can progress to the relevant work process.

Documents — Asset Documents

The Documents tab provides asset-specific document storage and retrieval. When a document is uploaded and associated with the asset, it becomes visible in this list.

  • Name — document/file name.
  • Type — file type such as JPEG.
  • Number and Validity — document metadata when provided.
  • Size — stored file size.
  • Actions — view/edit/download options according to permissions.

Readings — Asset Readings

The Readings tab records measurements or readings against the selected asset. The + button is used to create a new reading, and View Timeline provides the historical sequence of readings.

  • Use readings to maintain an asset-specific history, such as odometer-related values.
  • Each reading should be entered against the correct asset to preserve accurate maintenance/usage history.

Maintenance Policy — Asset-Level Assignment

Maintenance Policy is a separate module used to define maintenance rules or service intervals. When a maintenance policy is assigned to an asset, the applicable policy information becomes available in the asset's Maintenance Policy tab. This connects the asset to its maintenance schedule and supports tracking of service requirements.

  • Create/configure the maintenance policy in the Maintenance Policy module.
  • Select the applicable asset when assigning the policy.
  • Open Asset Details → Maintenance Policy to review the asset-specific policy.
  • Use the policy and asset readings/odometer information together when monitoring maintenance due requirements.

Section 3 — Fitness for Work

A self-assessment declaration the driver completes before starting duty.

A self-assessment declaration the driver completes before starting duty.

The driver answers Yes / No to nine compliance questions, covering rest hours, days off, fatigue, medication, alcohol/drugs, and correct sleeper-berth use. A progress indicator (e.g. “Answered 9 of 9”) confirms when the section is complete.

The nine questions

“Please answer all questions honestly before commencing duty.”

  1. Have you had at least 7 continuous hours of stationary rest in the last 24 hours?
  2. Have you had at least 24 hours off-duty in the last 7 days?
  3. Have you had at least 2 nights of stationary rest in the last 14 days?
  4. In the last 12 days, have you complied with all required rest conditions?
  5. Are you free from fatigue and fit to commence this shift?
  6. Have you had adequate sleep in the last 48 hours?
  7. Are you taking any medication that may affect your ability to drive safely?
  8. Have you consumed any alcohol or a drug that may impair your driving in the last 24 hours?
  9. Have you used a sleeper berth, and if so, was it used correctly as required?

Log Book — Submitting and Reviewing

What an admin can do with a Submitted Log Book, and what happens to Approved and Rejected ones.

Once Certification is complete, the Log Book is submitted for review and moves to the Submitted tab.

From the Submitted tab, an admin can:

  • View (eye icon) — open the full read-only detail.
  • Edit (pencil icon) — open the Log Book for correction.
  • Approve (green tick) — accept the Log Book; it moves to the Approved tab.
  • Reject (red cross) — send it back; it moves to the Rejected tab with a Red Flag.

Approved Log Books

An Approved Log Book becomes read-only. From here it can be Printed, Downloaded, or used to “Create Load Plan Sheet” (see Creating a Load).

Rejected Log Books

A Rejected Log Book can be reopened with “Edit and resubmit”. The driver corrects the flagged information, re-confirms the declaration, re-signs, and completes Certification again — after which it returns to the Submitted tab for another review.

Hierarchy groups related service policies so a higher eligible service can cover lower services. The critical order is: calculate eligibility first, then rank. A higher policy that has not reached its own trigger must not be pulled forward.

Concepts 1 to 4 — Meter Trigger OFF

Forecast generation: the reading side can fire before the actual due point.

Concept 1 — Variable + No Hierarchy + Meter Trigger OFF

Variable Cycle schedule, individual policy, forecast generation, no suppression.

  • Next Due = Last Done + Interval.
  • With Meter Trigger OFF, a reading interval can become eligible at the forecast trigger: Next Due – (Average Daily Usage x Lead Time).
  • Generating the Job Order does not advance Last Done. Last Done changes only when the Job Order is completed.
  • Example: Last Done 10,000 KM + 10,000 KM interval = 20,000 KM Next Due. At 1,000 KM/day with a 2-day lead, forecast trigger = 18,000 KM. If completed at 21,500 KM, new Next Due = 31,500 KM.

Concept 2 — Fixed + No Hierarchy + Meter Trigger OFF

Fixed Cycle schedule, individual policy, forecast generation, no suppression.

  • Next Due = Baseline + Interval.
  • With Meter Trigger OFF, forecast logic may generate before the actual due point.
  • At Job generation, the Baseline advances from the planned due point; actual completion does not move the future Fixed Cycle.
  • Example: Baseline 10,000 KM, interval 10,000 KM, Next Due 20,000 KM; forecast trigger may be 18,000 KM. Once generated, Baseline becomes 20,000 KM and Next Due becomes 30,000 KM, even if completion occurs at 21,500 KM.

Concept 3 — Variable + Hierarchy + Meter Trigger OFF

Variable Cycle with hierarchy, forecast generation, and suppression of covered lower services.

  • Each policy first calculates its own Next Due and must become independently eligible.
  • Only independently eligible policies enter hierarchy selection; the highest eligible level wins. A higher service must never be pulled forward just because a lower service is eligible.
  • At Job generation, Last Done remains unchanged for the generated policy and covered lower policies.
  • On completion, the generated and covered lower policies reset their Last Done anchors to the actual completion reading / date. Example: if B covers A and completes at 92,300 KM, A and B Last Done become 92,300 KM.

Concept 4 — Fixed + Hierarchy + Meter Trigger OFF

Fixed Cycle with hierarchy, forecast generation, and suppression of covered lower services.

  • Each hierarchy policy is evaluated independently before ranking.
  • At a common due point, the highest independently eligible service generates and covered lower services are suppressed.
  • Generated and covered lower baselines advance from their planned due points at Job generation.
  • Example: A 10K, B 30K, C 60K, D 120K. At 60K, C can generate and suppress A/B while D remains excluded if it is not independently eligible. Actual completion at 62,500 KM does not shift the fixed 60K anchor.

Concepts 5 to 8 — Meter Trigger ON

Actual-reading generation: the reading side fires on a new valid reading at or past Next Due.

Concept 5 — Variable + No Hierarchy + Meter Trigger ON

Variable Cycle schedule, individual policy, actual-reading Meter Trigger, no suppression.

  • Meter-side forecasting is disabled. Average usage is ignored for meter generation.
  • On a new valid matching reading, the condition is Current Reading >= Next Due Reading.
  • There is no hierarchy, so the policy is evaluated individually.
  • Last Done still changes only at Job completion. Example: Next Due 30,000 KM; 29,900 KM = no Job, 30,000 KM = eligible. If completed at 31,200 KM, the next cycle is calculated from 31,200 KM.

Concept 6 — Fixed + No Hierarchy + Meter Trigger ON

Fixed Cycle schedule, individual policy, actual-reading Meter Trigger, no suppression.

  • Meter generation waits for a new valid matching reading that is >= Next Due.
  • No average-usage forecast is used for the reading condition.
  • At Job generation, the Fixed Cycle Baseline advances from the planned due point.
  • Example: Baseline 20,000 KM and interval 10,000 KM gives Next Due 30,000 KM. At a valid 30,000 KM reading, generate the Job and advance Baseline to 30,000 KM; next due becomes 40,000 KM.

Concept 7 — Variable + Hierarchy + Meter Trigger ON

Variable Cycle with hierarchy, actual-reading Meter Trigger, and suppression.

  • Each hierarchy policy checks its own actual meter condition: new valid reading >= its own Next Due.
  • Only independently eligible policies become candidates; the highest eligible service wins and covered lower services are suppressed.
  • Generation does not update Last Done.
  • When the winning Job Order is completed, its actual completion reading / date resets the generated and covered lower policies. Higher policies that were not covered remain unchanged.

Concept 8 — Fixed + Hierarchy + Meter Trigger ON

Fixed Cycle with hierarchy, actual-reading Meter Trigger, and suppression.

  • Each policy independently compares the new valid reading with its own Next Due.
  • The highest independently eligible service generates; covered lower services are suppressed.
  • At generation, generated and covered lower baselines advance from their planned due points.
  • Example: A/B/C are due around 60K and D is due at 120K. At 60,250 KM, C is the highest eligible policy, so C generates, A/B are suppressed, and D is untouched.

Module 6 · Job Request · Decision & follow-through

Reviewing, Approving & Declining

The decision point — and the moment a Job Order is born.

  1. Go to the Open tab — this lists every request awaiting a decision.
  2. On the request row, click the three-dot icon (⋮) labelled More Action.
  3. Select View to open the full request details.
  4. Review the Asset, Priority and Description shown.
  5. Choose Approve if the work should go ahead, or Reject if it should not.
  6. If approved, the status changes to Approved, the request moves to the Approved tab, and a Job Order is created automatically.
  7. If declined, the status changes to Declined and the request moves to the Declined tab.

Module 6 · Job Request · Decision & follow-through

From Approved Request to Job Order

Where the request stops and the actual work begins.

  1. Open the Approved tab. Each row shows the Request name, Status (Approved) and Date.
  2. Click Actions on the request row, then click View.
  3. The detail screen shows the Asset, Priority, Description and other details of the request.
  4. Click View Job Order at the bottom of the screen.
  5. The Job Order page opens, showing Details, Instructions, Worklist, Material, Work Time, Document and Work Log.
  6. From here you can edit details, add a Work Log entry, and make changes as the job progresses.
  7. When the work is finished, mark the Job Order Complete and Sign Off — or mark it Cancel if the job is not going ahead.

Learning Document is used when training material is an actual file—such as an image, PDF or Word file—combined with multiple-choice questions. It also supports a Refresher Interval in days.
